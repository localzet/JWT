# Localzet JWT

Библиотека PHP 8.2+ для компактных подписанных JSON Web Token. Ожидаемый алгоритм и доверенный ключ задаёт приложение; библиотека не выбирает их по неподтверждённому токену.

[English documentation](README.md) · [Семейство токенов](https://github.com/topics/localzet-tokens)

## Пример

```sh
composer require localzet/jwt
```

```php
use localzet\JWT;

$key = random_bytes(32);
$token = JWT::encode(['sub' => 'user-id', 'exp' => time() + 300], $key, 'HS256');
$claims = JWT::decode($token, $key, 'HS256');
```

Ключ примера временный; рабочие ключи храните в защищённом хранилище. Подпись не шифрует содержимое — claims доступны для чтения.

Поддерживаются HS256/384/512, RS256/384/512, ES256/384/512 и EdDSA с сырыми ключами Ed25519 libsodium. Для HMAC нужно минимум 32/48/64 байта соответственно; PEM вместо симметричного ключа отклоняется. RSA требует минимум 2048 бит. ECDSA использует P-256/P-384/P-521 и формат подписи JWA `R || S`. Ключи OpenSSL передаются как PEM, Ed25519 — как байты закрытого/открытого ключа libsodium. Composer требует OpenSSL, JSON и mbstring; для EdDSA дополнительно нужен sodium.

`decode()` проверяет подпись до выдачи claims, типы NumericDate и срок `exp`/`nbf`, если они есть, без допуска расхождения часов. Claims должны быть JSON-объектом. Приложение само требует `exp` при необходимости и проверяет ожидаемые issuer, audience, subject, scope и назначение токена. `kid` — метаданные, а не доверенная инструкция выбора ключа. Неизвестные критические заголовки и неподкодированные payload отклоняются. JWE и общая JSON-сериализация JWS не поддерживаются.

## Миграция старых токенов

Изменения устраняют небезопасное/нестандартное поведение и требуют отдельного нового релиза:

- HMAC использует симметричный ключ напрямую, а не прежнее получение секрета из PEM;
- ECDSA использует фиксированный `R || S`, а не DER в JWT-сегменте;
- SHA-1, усечённый HS256/64, ES256K, `none` и незавершённый RSA-PSS отклоняются;
- некорректный base64url, неподходящие ключи и недействующие по времени claims отклоняются;
- алгоритм и ключ обязательны; их отсутствие вызывает контролируемое исключение.

Старые нестандартные токены нужно перевыпустить по управляемой процедуре. Не добавляйте автоматический fallback, принимающий оба формата. Публичные сигнатуры `encode/decode` и свойства дополнительных заголовков сохранены. Незавершённые JWE/JWK/JWS не являются готовым API.

## Проверка

```sh
composer validate --no-check-publish
composer test
```

Проверяются публичный HMAC-вектор RFC 7515, HMAC/RSA/ECDSA/Ed25519, совместимость с OpenSSL, несовпадение алгоритма/ключа, некорректные кодировки, сроки claims и подмена данных. CI проверяет PHP 8.2–8.5. Это не независимый криптографический аудит. Публикация в Packagist выполняется отдельно.

Спецификации: [RFC 7515](https://www.rfc-editor.org/rfc/rfc7515), [RFC 7518](https://www.rfc-editor.org/rfc/rfc7518), [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725). Лицензия AGPL-3.0-or-later.
